## 已取得的故障证据

手机 V2419A / PD2419，分身 user999，UID 99910400。系统 exit-info 保存以下记录：

| 进程 | PID | 退出时间 | 系统原因 |
|---|---:|---|---|
| 闲鱼主进程 | 16854 | 20:25:18.422 | reason=6，ANR |
| channel | 17180 | 20:25:29.505 | reason=6，ANR |
| 闲鱼主进程 | 18852 | 20:34:18.227 | reason=6，ANR |
| channel | 19673 | 20:34:29.672 | reason=6，ANR |

20:33 的启动中，PID 18852 记录六项屏蔽全部加载，native compatibility 与设备 native 层初始化成功。随后系统 ANR 文件中，目标主线程多次显示 futex_wait_queue。

两份目标 ANR 文件只取得 OEM 的 Waiting Channels，未取得目标进程的 ART Java 栈。文件内其他进程的 Java 栈不作为闲鱼的栈。对 PID 18852 的 debuggerd 采集在 15 秒限时内失败；这次启动包含诊断操作，不能作为完全未干预的启动对照。20:25 的既有 ANR 则早于这次采集。现有证据没有指出具体 Java 方法、native 调用者或持锁线程。

上述事实确认了“卡住后被系统结束”，没有确认 MTOP 请求、服务器签名错误或网络状态返回错误。

最后一次使用桌面入口对应的 InitActivity、MAIN / LAUNCHER 和 0x10200000 flags，通过 vivo 选择器选择分身。PID 9556 实际记录：

- ART code views=8，native compatibility ready=1。

- DeviceProfile native ready hooks=3 objects=1。

这排除了“最后一次因为没有注入，所以能启动”的解释。其 syscall broker 线程处于 seccomp_notify_ioctl 等待，主线程也有正常运行采样。界面只保存资源 ID、标准导航标签和所属用户，没有保存页面内容、账号字段或登录凭据。页面存在 login_guide_bar，登录后请求仍未验证。

关闭机器伪装后的启动结果曾使它成为候选原因；恢复完整原配置仍能启动，因此不能把这一结果写成“机器伪装已被证实导致 ANR”，也不能把重新保存开关写成永久修复。
